# サブエージェント用プロンプトテンプレート

並列実行するサブエージェントに渡すプロンプト。プレースホルダ `{{ ... }}` は呼び出し時に展開する。

すべてのサブエージェントは `general-purpose` を使用し、明示的に `model: "sonnet"` を指定する。

## 目次

- 共通の原則（すべてのサブエージェントに適用）
  - 信頼性の原則
- ステップ別プロンプト
  - Step 2: ページ構造抽出
  - Step 3: アクション抽出
  - Step 8: ページに参照モデルを追記
  - Step 11: ページに利用コンポーネントを追記
  - Step 13: ページ末尾に「関連する未解決事項」を追記
- 補足
  - ステップ単位の並列起動の Tips
  - Sonnet で十分な根拠
  - Opus が必要な根拠

## 共通の原則（すべてのサブエージェントに適用）

- Figma に明示されていない属性は推測補完しないが、**ページ名称・構成要素・アイコン・親要素から客観的に導ける範囲では補完する**（SKILL.md の「補完しない原則 と 客観抽出の許容範囲」参照）
- ID 命名は SKILL.md の規則に従う
- 出力 Markdown の骨組みは [`output-templates.md`](output-templates.md) を参照
- ID を記載する際は必ず Entity 名／カラム名／コンポーネント名を併記する（例: `` `E-02.C-06`（AwardEdition.application_close_at） ``）

### 信頼性の原則（iter 5 以降必須）

すべてのサブエージェントは以下の規則を厳守：

1. **対象ファイル以外への Edit 禁止**
   - プロンプトで「対象ファイル」と明示されたファイル **1 つのみ** に Edit を適用
   - その他のファイル（data-model.md、components.md、レビュー 3 種など）は **Read のみ**
   - 「対象ファイル以外を編集しようとして失敗した」というケースが過去に発生したため、絶対に違反しないこと

2. **ID 番号の幻覚禁止**
   - Entity ID（E-XX）、カラム ID（E-XX.C-YY）、コンポーネント ID（CMP-XX）は **必ず参照元ファイル（data-model.md / components.md）から実在するものをコピー** すること
   - 記憶ベースで `E-30`、`CMP-70〜78`、`SearchQuery` 等の架空 ID を作らない
   - 親エージェントがプロンプトに「使用可能な ID リスト」を提供する場合があるので、そのリスト外は使用禁止

3. **完了前のセルフチェック**
   - Edit 完了後に **必ず** 対象ファイルを Read し、追記したセクション（正確なセクション名）が存在することを確認
   - 期待するセクション名（例: `## 参照モデル` / `## 利用コンポーネント` / `## 関連する未解決事項`）が **そのままの文字列で存在** することを確認
   - 「## データモデル」「## コンポーネント」「## レビュー」等の誤った見出しを書いていないこと

4. **完了報告の正直性**
   - 完了報告には「実際に編集したファイル名」「実際に追記したセクション名（正確な文字列）」を含める
   - 編集に失敗した場合は失敗と明示し、虚偽報告しない

## Step 2: ページ構造抽出（model: sonnet）

```text
あなたは Figma のワイヤーフレームから、特定ページの構造を Markdown にまとめるアシスタントです。

## 入力
- Figma fileKey: {{fileKey}}
- 対象ページ名: {{pageName}}
- 対象ノードID: {{nodeId}}
- 出力先パス: docs/pages/{{slug}}.md

## 作業手順
1. /figma-use スキルを Skill ツールでロード（use_figma 呼び出し前に必須）
2. mcp__plugin_figma_figma__use_figma で対象ノードの階層を深さ 3 で取得:
   ```js
   const targetId = "{{nodeId}}";
   function summarizeNode(node, depth, maxDepth) {
     if (depth > maxDepth) return null;
     const info = { id: node.id, name: node.name, type: node.type,
       w: 'width' in node ? Math.round(node.width) : null,
       h: 'height' in node ? Math.round(node.height) : null };
     if (node.type === 'TEXT') info.text = (node.characters || '').slice(0, 400);
     if ('children' in node && node.children && depth < maxDepth) {
       info.children = node.children.map(c => summarizeNode(c, depth + 1, maxDepth)).filter(Boolean);
     } else if ('children' in node && node.children?.length) {
       info.childrenCount = node.children.length;
     }
     return info;
   }
   const page = figma.root.children[0];
   await figma.setCurrentPageAsync(page);
   const node = await figma.getNodeByIdAsync(targetId);
   return summarizeNode(node, 0, 3);
   ```
3. テキストが詰まっていない深い領域は深さ 4 で追加取得

## 出力フォーマット
docs/pages/{{slug}}.md を以下の構造で生成:

# {{ページ名}}

- **ノードID**: `{{nodeId}}`
- **キャンバスサイズ**: {{w}} × {{h}} px
- **ページの役割概要**: {{ページ名称＋構成要素から導ける役割を 1〜2 文で記述}}

## 構成要素

| # | 構成要素名 | 種類 | ノードID | 役割概要 |
|---|---|---|---|---|
| 1 | ... | FRAME / TEXT / ... | `xxx:yyy` | ... |

## テキスト要素一覧
（各構成要素内のテキスト要素を 1 表に集約。詳細は下記「## 「## テキスト要素一覧」セクション」参照）

## ページ役割概要のルール（重要）

「ページの役割概要」は **ページ名称＋構成要素から客観的に導ける範囲で 1〜2 文で記述する**:

- 例 1: トップページ → 「秋田書店まんが賞ポータルのランディングページ。注目賞のヒーロー表示、ステータスフィルター付き賞カード一覧、ニュース、特集記事、Web 持ち込み CTA で構成される。」
- 例 2: FAQ → 「秋田書店まんが賞ポータルの FAQ ページ。キーワード検索、カテゴリ別 FAQ（応募について／選考・結果について）、お問い合わせ誘導カードで構成される。」
- 例 3: 完全に推測になる場合のみ「Figma 未記載」（ページ名が一般的すぎる、構成要素から目的が一意に決まらない 等）

## 役割概要のルール（構成要素表）

「役割概要」列は **構成要素名＋種類＋子要素から客観的に導ける範囲で 1 文で記述する**:
- 例: 「Header (`98:64`、FRAME)」→ 「ページ上部のナビゲーションヘッダー（サイトロゴ＋メニューアイコン）」
- 子要素がテキスト 1 つだけ等で機能が一意に決まらない場合のみ「Figma 未記載」

## 「## テキスト要素一覧」セクション（旧「## 詳細」、表形式に強制）

セクション名を **`## テキスト要素一覧`** に変更し、表 1 つに集約：

```markdown
## テキスト要素一覧

各構成要素内のテキスト要素（見出し文言、コピー、ボタンラベル、プレースホルダー）を 1 表にまとめる。

| ノードID | 種別 | テキスト（Figma 表記そのまま） |
|---|---|---|
| `98:66` | TEXT | 「秋田書店まんが賞」 |
| `98:79` | TEXT | 「募集状況で絞り込み」 |
| `98:81` | TEXT | 「募集中」 |
```

### ルール
- **表 1 つに集約**（H3 で構成要素別に分けない、散文での構造説明をしない）
- TEXT ノードのみ列挙（FRAME や VECTOR は構成要素表で扱う）
- プレースホルダー文字列（「[賞のビジュアル]」「[写真]」等）も含める
- **15〜25 行程度** が目安（200 行超のページでも、TEXT ノードは絞られる）

## 制約
- 「アクション」「データソース」「コンポーネント」関連のセクションは作らない（後段ステップで追記）
- テキストは Figma 表記をそのまま転記（半角・全角を変えない）
- 200KB 超の出力にしない（深さは最大 4 まで）

## 完了報告
ファイル作成完了後、以下を 100 字以内で返す:
- 抽出した構成要素の総数
- 「ページの役割概要」を客観抽出で書いたか／Figma 未記載か
```

## Step 3: アクション抽出（model: sonnet）

```text
あなたは指定ページの Markdown から、ユーザーアクションを伴う UI 要素を抽出して追記するアシスタントです。

## 入力
- 対象ファイル: docs/pages/{{slug}}.md
- ページ名: {{pageName}}

## 作業手順
1. Read で docs/pages/{{slug}}.md を全行読む
2. 構成要素のうち、ユーザー操作に応答するものを抽出
3. Edit で「## テキスト要素一覧」の末尾に「## アクションボタン」セクションを追加

## アクション種別の語彙（この中から選ぶこと）
- ページ遷移
- ページ遷移（外部リンク）
- ページ内アンカー
- オーバーレイ表示
- オーバーレイ閉じる
- 一覧フィルター
- スライド切替
- アコーディオン展開/折りたたみ
- テキスト入力＋検索送信
- 履歴戻る

## 挙動概要のルール（重要）

「挙動概要」は **構成要素名・親要素・アイコン・周辺コンテキストから客観的に導ける範囲で 1 文で記述する**:

- 例 1: ヘッダー左端の Arrow Left → 「タップで前画面に戻る（履歴戻る）」
- 例 2: フッターの「運営会社について」リンク → 「タップで運営会社紹介ページへ遷移する」
- 例 3: 賞カード（Award Card） → 「タップで該当賞の詳細ページへ遷移（賞の status により詳細（募集中）or 詳細（結果発表）に振り分け）」
- 例 4: 完全に推測になる場合のみ「Figma 未記載」（遷移先が一意に決まらないタグ、外部リンクで具体的な遷移先が不明 等）

## 出力フォーマット（ソース列付）

## アクションボタン

| # | 構成要素名 | ノードID | アクション種別 | 挙動概要 | ソース |
|---|---|---|---|---|---|
| 1 | ... | `xxx:yyy` | ページ遷移 | {{挙動}} | Figma 明示 / 客観推定 / Figma 未記載 |

### 「ソース」列の判定基準（重要・厳密化）

- **Figma 明示**: Figma の **Prototype Reactions パネルで明示的に reaction が設定されている場合のみ**（例: 「On Click → Navigate to Frame `98:778`」）。`use_figma` の `node.reactions` 配列の長さで判定可能
  - ❌ アイコンの向き（Chevron Down / Chevron Right）→ これは UI 状態（展開/折り畳み）であって reaction ではない
  - ❌ 色・アクティブ状態（Filter Active / Inactive）→ これも UI 状態であって reaction ではない
  - ❌ テキスト表記（「Web投稿はこちら」「お問い合わせ」）→ ラベルであって reaction ではない
- **客観推定**: それ以外で構成要素名・アイコン・親要素・周辺コンテキストから挙動が客観的に導けるもの。**ワイヤーフレームレベルの Figma では多数派**
- **Figma 未記載**: 完全に推測になる場合のみ（遷移先候補が複数あって一意に決まらない等）

### Source 列の集約表示ルール（冗長性削減）

全アクションが同一ソース（例: 全件「客観推定」）の場合、表ヘッダー直前に注記して **ソース列を省略**:

```markdown
## アクションボタン

**ソース**: 全件「客観推定」（このページのプロトタイプ Reactions は未設定）

| # | 構成要素名 | ノードID | アクション種別 | 挙動概要 |
|---|---|---|---|---|
```

混在の場合（Figma 明示と客観推定が両方ある等）のみ Source 列を残す。

## 制約
- 表示専用要素（テキスト・装飾）は対象外
- ノードID を必ず記載
- 既存セクションを変更しない

## 完了報告
追記完了後、アクション数と「ソース別の内訳」（Figma 明示 X 件 / 客観推定 Y 件 / Figma 未記載 Z 件）を返す
```

## Step 8: ページに参照モデルを追記（model: sonnet）

```text
あなたは指定ページの表示要素を、データモデルの Entity.カラム にマッピングして追記するアシスタントです。

## 対象ファイル（**Edit はこのファイルにのみ**）
- docs/pages/{{slug}}.md

## 参照ファイル（**Read のみ、Edit 禁止**）
- docs/data-model.md

## 使用可能な Entity リスト（このリスト外の番号を使わない）

{{親エージェントが data-model.md から抽出したリストをここに展開}}

例:
- `E-01` AwardSeries
- `E-02` Award
- `E-03` Prize
- ...
- `E-22` SiteSetting

**警告**: 上記リスト外の番号（例: `E-30`、`SearchQuery` などの架空名）を絶対に使わない。記憶ベースで番号を捏造しないこと。

## 作業手順
1. Read で docs/pages/{{slug}}.md と docs/data-model.md を読む
2. データモデルの全 Entity と E-XX.C-YY を頭に入れる
3. ページ上の各表示要素について対応する E-XX.C-YY を特定
4. Edit で「## アクションボタン」の直後に「## 参照モデル」セクションを追加

## 集約ルール（重要・冗長性削減）

- **同一カラムを参照する複数の表示要素は集約**: 「賞名（ヘッダー）」「賞名（カード）」を別行で並べず、1 行に「賞名（複数箇所）」と書く
- **静的文言は 1 行にまとめる**: フッターリンクラベル 3 件（運営会社／プライバシー／お問い合わせ）を別行で書かず、1 行に集約
- **セクションあたりの行数の目安は 8 行以内**（10 を超えそうな場合は集約方針を再検討）

## 「静的」と「対応モデル未定義（要レビュー）」の判別ルール（重要）

以下は **「静的」** として記録する（「対応モデル未定義」とは書かない）：

- ナビゲーション UI: Arrow Left（戻る）、Menu アイコン、X 閉じるボタン、Chevron アイコン
- 装飾 UI: Divider、罫線、背景パターン、SectionHeader のアイコン円
- セクション見出しの固定文言: 「賞金・特典一覧」「審査員紹介」「過去の結果を見る」「総評」「お知らせ」など、サイトの構造を示す見出し
- アイコン全般: 用途名のみで遷移先や動的データを示さない（Calendar、Clock、Trophy、Upload 等）
- プレースホルダー UI: 「[賞のビジュアル]」「[作品表紙画像]」「[写真]」など、画像位置を示すプレースホルダーテキスト自体

**「対応モデル未定義（要レビュー）」を使うのは、動的データが必要だが該当 Entity / カラムが存在しない場合のみ**:
- 例: 「会員ステータス」表示がページにあるが、`User` Entity が存在しない → 対応モデル未定義（要レビュー）
- 例: 「お気に入り数」表示があるが、Like 系 Entity が存在しない → 対応モデル未定義（要レビュー）

判断に迷う場合は **「静的」を選ぶ**。ノイズが多くなるよりはレビュー網羅性が下がる方が許容範囲。

## 出力フォーマット

## 参照モデル

各構成要素が参照する Entity のカラムをマッピング。詳細は [`docs/data-model.md`](../data-model.md) 参照。

### {{セクション名}} (`{{nodeId}}`)
| 表示要素 | 参照 |
|---|---|
| {{表示テキスト or 要素名}} | `E-XX.C-YY`（{{Entity名}}.{{カラム名}}） |
| {{ハードコード文言}} | 静的 |
| {{該当無し}} | 対応モデル未定義（要レビュー） |

### 利用 Entity サマリー
`E-XX`, `E-YY`, ...

## 制約
- 必ず E-XX.C-YY 形式で記載（Entity 名やカラム名だけの参照は不可）
- データモデルに対応が見当たらない要素は **「対応モデル未定義（要レビュー）」** と書く（勝手にカラムを増やさない）
- 静的文言は「静的」で統一
- 既存セクションを変更しない

## 完了前のセルフチェック（必須・iter 5 以降）

Edit 完了後に対象ファイル `docs/pages/{{slug}}.md` を Read し、以下を確認：

1. **正確なセクション名 `## 参照モデル` がそのまま存在する**（「## データモデル」「## モデル参照」等の誤名でない）
2. **使用した Entity ID がすべて「使用可能な Entity リスト」に含まれる**（リスト外の番号を使っていない）
3. 既存セクション（`## 構成要素` / `## テキスト要素一覧` / `## アクションボタン`）が変更されていない

## 完了報告（正直に）

- 編集したファイル名: `docs/pages/{{slug}}.md`（**対象ファイルと一致しているか確認**）
- 追記したセクション名: `## 参照モデル`（**正確な文字列**）
- 利用 Entity 数 と使用した Entity ID リスト（リスト外がないこと）
- 「対応モデル未定義（要レビュー）」となった要素数
- 集約効果（参考。「素朴に列挙すると X 行 → 集約後 Y 行」）

セルフチェックで問題があった場合は **失敗を明示** し、虚偽報告しないこと。
```

## Step 11: ページに利用コンポーネントを追記（model: sonnet）

```text
あなたは指定ページの構成要素に、定義済みコンポーネント（CMP-XX）を割り当てて追記するアシスタントです。

## 対象ファイル（**Edit はこのファイルにのみ**）
- docs/pages/{{slug}}.md

## 参照ファイル（**Read のみ、Edit 禁止**）
- docs/components.md

## 使用可能な CMP リスト（このリスト外の番号を使わない）

{{親エージェントが components.md から抽出したリストをここに展開}}

例:
- `CMP-01` Text（Atom）
- `CMP-02` Icon（Atom）
- ...
- `CMP-41` Header（Organism）
- `CMP-67` MenuOverlay（Organism）
- `CMP-80` StandardPageTemplate（Template）
- `CMP-81` OverlayTemplate（Template）

**警告**: 上記リスト外の番号（例: `CMP-70`〜`CMP-78` の架空連番）を絶対に使わない。記憶ベースで番号を捏造しないこと。

## 作業手順
1. Read で docs/pages/{{slug}}.md と docs/components.md を読む
2. コンポーネント定義の全 CMP-XX を頭に入れる
3. ページ上の構成要素のうち **Organism / Template / 主要 Molecule** を特定（Atom 内包要素は除外）
4. Edit で「## 参照モデル」の直後に「## 利用コンポーネント」セクションを追加

## 集約ルール（重要・冗長性削減）

- 出力対象は **Organism / Template / 主要 Molecule のみ**
  - Atom レベル（Icon、Text、Divider、Image Placeholder 等）はコンポーネント定義側で Organism に内包されているため、ページ単位での明示は不要
  - 例: AwardCard を 1 行記載すれば足り、その中の Icon / Text / Image を別行で書く必要は無い
- 同一コンポーネントの複数利用箇所は「利用箇所数」に集計（ノードID の箇条書きはしない）
- 「ページ全体レイアウト」として最後に Template（例: `CMP-60` StandardPageTemplate）を 1 行記載

## 出力フォーマット

## 利用コンポーネント

各構成要素が利用するコンポーネント（Organism 中心）。詳細は [`docs/components.md`](../components.md) 参照。

| # | 構成要素名 | ノードID | コンポーネント | 利用箇所数 |
|---|---|---|---|---|
| 1 | Header | `98:64` | `CMP-31`（Header） | 1 |
| 2 | Hero Section | `98:71` | `CMP-33`（HeroSlider） | 1 |
| ... | ... | ... | ... | ... |
| N | ページ全体レイアウト | `{{page_root_id}}` | `CMP-60`（StandardPageTemplate） | 1 |

## 制約
- 必ず CMP-XX 形式で記載

## ステップ単位の並列起動の Tips

- **1 メッセージ内で複数 Agent 呼び出しを並べる** とすべて並行実行される
- 失敗時のフォールバックは親エージェントが直接リトライ（Sonnet → Opus）
- 各サブエージェントには `description` を 10〜15 字程度（例: `top 構造抽出`）で付け、進行表示を簡潔に
- サブエージェントは context 共有しないため、必要な情報はすべて prompt に含める（特に fileKey, nodeId, ファイルパス）
- ID 規則を守らせるため、プロンプト内で **「E-XX.C-YY 形式で書く」「CMP-XX 形式で書く」** と明示する
