# extension モード（既存リポジトリの機能拡張）詳細ガイド

`extension` モードでは、Figma で定義された機能拡張を既存リポジトリに追加するため、既存資産（モデル・ルーティング・ビュー）の再利用を最優先する。本ガイドは Step 0.5 / Step 7 / Step 10 における extension モード固有の振る舞いを記述する。

## Step 0.5: 既存コードベース調査

### 目的

Figma 抽出の前に既存リポジトリの主要資産を調査し、Step 7 / 10 / 14 で「既存資産再利用」の判断材料を揃える。

### 調査対象（言語・フレームワーク非依存のコアセット）

1. **既存モデル定義**
   - Rails: `app/models/**/*.rb` + `db/schema.rb` または `Schemafile`
   - Next.js: `prisma/schema.prisma` または `models/**/*.ts`
   - 各モデルの **テーブル名・主要カラム・既存スコープ・既存メソッド** を整理

2. **既存ルーティング**
   - Rails: `config/routes.rb`
   - Express: `routes/**/*.ts`
   - Next.js: `app/**/page.{ts,tsx}`

3. **既存ビュー / UI 資産**
   - Rails: `app/views/**/*.{slim,erb,haml}`
   - React: `components/**/*.{tsx,jsx}`

4. **既存設定**
   - `config/application.yml` / `.env.example` / Settingslogic / dotenv

5. **既存管理画面**
   - 管理画面 Engine / 管理画面ビューの有無

### 出力ファイル

`docs/existing-codebase.md` を新規作成し、以下の構造で整理：

```markdown
# 既存コードベース調査結果

**調査日**: YYYY-MM-DD
**リポジトリ**: {{プロジェクト名}}
**フレームワーク**: {{Ruby on Rails X.Y / Next.js X.Y 等}}

## 既存モデル一覧

| モデル名 | テーブル名 | 主要カラム | 既存スコープ／メソッド | Figma 関連度 |
|---|---|---|---|---|
| ... | ... | ... | ... | **高 / 中 / 低 / 無関連** |

## 既存ルーティング（Figma 関連のみ）

| パス | コントローラ#アクション | 用途 |
|---|---|---|

## 既存ビュー資産

| ビュー | 用途 | リニューアル後の扱い |
|---|---|---|

## 既存設定

| 設定キー | 用途 |
|---|---|

## 再利用候補のサマリー

| 用途 | 既存資産 | 推奨アクション |
|---|---|---|
| ... | ... | **そのまま再利用 / カラム追加 / 新規追加** |
```

### サブエージェント実行（推奨）

Sonnet サブエージェント 1 つで調査を委譲。プロンプトは [`sub-agent-prompts.md`](sub-agent-prompts.md) の Step 0.5 セクション参照。

### 重要事項

- すべての既存モデルを列挙せず、**Figma の機能拡張と関連しそうな** モデルに絞る
- 「Figma 関連度」は **高 / 中 / 低 / 無関連** の 4 段階で明記
- 「再利用候補のサマリー」は後続 Step 7 / 14 で参照される最重要セクション

## Step 7 拡張: データモデル抽出での既存資産優先

### 設計優先順位

新規 Entity を作る前に、以下の優先順位で既存資産の活用を検討：

1. **既存モデルそのまま再利用**: Figma の表示要素を既存カラムだけで表現できる場合
2. **既存モデルにカラム追加で対応**: 既存モデルの拡張で表現可能な場合
3. **既存カラムの用途流用**: 既存利用との衝突が無いカラム。**衝突有無は実コード grep で確認必須**
4. **新規 Entity 作成**: 上記で対応できない場合のみ

### `docs/data-model.md` の追加必須セクション（extension モードのみ）

- **既存モデル（再利用 / 拡張）**: 再利用モデルの一覧。拡張要否を「拡張不要」「要拡張」で明示
- **既存モデルへのカラム追加**: 表形式で（テーブル名・カラム名・型・説明・影響 Figma 要素）
- **取り下げた Entity 案**: 設計初期に検討したが既存資産で代替できると判明し取り下げた Entity の根拠表

### 既存利用との衝突確認（必須）

カラムを別用途で流用する案を採用する前に、以下を **必ず実コードで確認**：

```bash
# 例: ContestGroup.description を編集部メッセージに流用する案を検討する場合
grep -rn "contest_group.description\|@contest_group.description" app/ --include="*.{rb,slim,erb}"
```

衝突発見時は data-model-review.md の必須項目に明記し、Step 14 のレビュー反復で再検討する。

## Step 10 拡張: コンポーネント抽出での既存 UI 資産考慮

### 設計優先順位

1. **既存 UI コンポーネントそのまま再利用**: 既存に Header / Footer 等の共通コンポーネントがあれば再利用
2. **既存コンポーネントを拡張**: variant 追加・props 追加で対応
3. **新規コンポーネント作成**: 上記で対応できない場合のみ

### `docs/components.md` の追加必須セクション（extension モードのみ）

- **既存 UI 資産との対応**: Figma の Organism/Molecule と既存ビュー（partial / コンポーネント）の対応表
- **既存スタイル資産**: 既存 SCSS 変数・CSS Variables・デザインシステムの活用

### 既存 UI 資産との衝突確認

既存ビューパス（例: `app/views/shared/_header.html.slim`）と Figma の Header コンポーネントの差分を整理し、リニューアル後の取り扱い（置き換え / 拡張 / 並行運用）を明記する。
