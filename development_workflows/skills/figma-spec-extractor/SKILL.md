# Figma Spec Extractor

このスキルは Figma のワイヤーフレームから仕様書一式を段階的に抽出し、`docs/` 配下に Markdown で出力する。**Figma に明示的に無い属性は推測補完しない** が、Figma の構成要素から客観的に導ける範囲（ページ役割、状態遷移、CMS／SEO 観点の設計示唆、アクターの典型ペインポイント等）は本体に含めて、ドキュメントの実装利用価値を高める。

## 当該スキルが扱う出力

```
docs/
├── pages/
│   ├── README.md                    # ページインデックス + 横断サマリー
│   └── <page-slug>.md               # 各ページの構成要素・アクション（ソース付）・参照モデル・コンポーネント・関連未解決事項
├── use-cases.md                     # ユースケース一覧
├── actors.md                        # アクター一覧（全アクター列を持つ UC×Actor マトリクス含む）
├── data-model.md                    # Entity / Relation 定義 + 状態遷移 + 設計上のメモ
├── components.md                    # 共通化方針サマリー + Atomic Design コンポーネント定義 + ページ→Organism マッピング検証表
└── reviews/
    ├── coverage-review.md           # ゴール×UC×Actor×Page×Action の不足検出（優先度ラベル付）
    ├── data-model-review.md         # データモデルの不足検出（優先度ラベル付）
    └── components-review.md         # コンポーネントの不足検出（優先度ラベル付）
```

## ID 命名規則（スコープ付き）

すべての主要要素にスコープ付き ID を付与する。

| 対象 | ID 形式 | 例 |
|---|---|---|
| ユースケース | `UC-XX` | `UC-01` |
| アクター | `A-XX` | `A-01` |
| Entity | `E-XX` | `E-01` |
| Entity のカラム | `E-XX.C-YY` | `E-01.C-03` |
| Entity のインデックス | `E-XX.I-YY` | `E-01.I-01` |
| Relation | `R-XX` | `R-01` |
| コンポーネント | `CMP-XX` | `CMP-01` |
| コンポーネントのパラメータ | `CMP-XX.P-YY` | `CMP-01.P-02` |
| コンポーネントのイベントハンドラ | `CMP-XX.H-YY` | `CMP-01.H-01` |

数字は **発見順にゼロパディング 2 桁** で採番。後続ステップで参照する際は必ずこの ID を使う。ID 記載時は **必ず Entity 名／カラム名／コンポーネント名を併記** する（例: `` `E-02.C-06`（AwardEdition.application_close_at） ``）。

## 補完しない原則 と 客観抽出の許容範囲

### 禁止（推測補完）
- Figma に存在しない属性（業務要件、KPI、戦略目標）を勝手に書き起こす
- 「ありそう」な追加機能（例: ユーザー登録、認証、決済）を勝手に追加する
- ペルソナの架空属性（具体的な年齢、職業、家族構成 等）をでっち上げる

### 許容（客観抽出。本体ドキュメントに記述してよい）
- **ページ名称＋構成要素から導ける役割記述**（例: 「FAQ ページ。検索／カテゴリ別 FAQ／お問い合わせ誘導で構成される」）
- **属性の状態遷移／ライフサイクル**（ENUM 値自体は Figma にあるため、遷移図化は補完ではなく可視化）
- **CMS／運用／SEO の設計示唆**（Figma の構成から自然に導出されるベストプラクティス、例: ブロックエディタ推奨、JSON-LD FAQ 対応など）
- **アクターの分類（プライマリ／セカンダリ／オフステージ）と典型ペインポイント**（Figma の解決対象である UI 要素から逆算）
- **アクションの挙動概要**（構成要素名＋親要素＋アイコンから一意に決まるもの。例: ヘッダー左の Arrow Left → 「履歴を戻る」）

### Figma 未記載のままにする項目
レビューステップ（Step 6 / 9 / 12）で初めて不足を列挙し、ユーザーに提示する。本体側で「未記載」と書くのは、上記「許容」にも当てはまらない場合のみ。

## 前提条件

1. `plugin:figma:figma` MCP が認証済み（未認証なら `/mcp` で認証を促す）
2. 出力先のディレクトリで作業中
3. ユーザーから以下を取得済み：
   - Figma URL（`https://www.figma.com/design/:fileKey/...`）
   - **プロジェクトのゴール**（レビュー時の評価軸として必須）
   - **転記先**（ローカル Markdown のみ／Notion／GitHub Wiki 等。リンク表記の切替に使用）

## 実行モード

**ハイブリッドモード（推奨デフォルト）**:
- Step 0（準備）と Step 1（ページ一覧）でユーザー確認を挟む
- Step 4（UC 一覧）と Step 7（データモデル Entity 一覧）の直後にもサマリ確認を挟む（軌道修正の機会）
- レビューステップ（Step 6 / 9 / 12）の結果は **修正適用せず提示のみ**

**全自動モード**:
- ユーザーが「自動で進めて」と明言した場合、Step 1〜12 をユーザー確認なしで進める
- レビューステップの提示は省略不可

## ステップ詳細

各ステップで使うプロンプト・出力フォーマットは：

- [`references/sub-agent-prompts.md`](references/sub-agent-prompts.md) — サブエージェント用プロンプト
- [`references/output-templates.md`](references/output-templates.md) — 出力 Markdown の骨組み

### Step 0: 準備

1. ユーザーから以下を確認：
   - **Figma URL**（無ければ依頼）
   - **プロジェクトのゴール**（無ければ依頼。レビューで利用するため必須）
   - 出力ディレクトリ（デフォルト `docs/`）
   - **転記先**（ローカル／Notion 等）→ Notion 等の場合、相対パスリンクは使わず「{{ファイル名}}（別ページ）」表記に切替
2. URL から `fileKey` を抽出
3. `docs/pages/` と `docs/reviews/` を作成
4. 既存 `docs/` の有無を確認し、上書きの可否を確認
5. プロジェクトゴールを `docs/reviews/coverage-review.md` の先頭に保存（後続レビューで参照）

### Step 1: ページ一覧抽出

1. `figma-use` スキルをロード
2. `use_figma` で全ページ／トップレベルフレームを列挙：
   ```js
   const result = [];
   for (const page of figma.root.children) {
     await figma.setCurrentPageAsync(page);
     result.push({
       pageId: page.id, pageName: page.name,
       topNodes: page.children.map(c => ({
         id: c.id, name: c.name, type: c.type,
         width: 'width' in c ? c.width : null,
         height: 'height' in c ? c.height : null,
       })),
     });
   }
   return result;
   ```
3. 実装対象を判定（Slice や注釈帯は除外）
4. **キャンバスサイズ自動検出**:
   - 全実装対象ページの width を集計し、一意な値が 1 つしか無い場合（例: 全ページ 390px）→ 「単一幅設計（モバイル想定）」と判定し、`docs/pages/README.md` の「未確認・要追加情報」に「**PC（デスクトップ）レイアウト**: 本 Figma ファイルにはモバイル幅（{{width}}px）のみ存在。レスポンシブ仕様は別途確認が必要」を自動追記
   - 一意な値が 2 つ以上ある場合（例: 390 / 1440）→ レスポンシブ対応済みと判定
5. **プロトタイプ Reactions の有無検出**:
   - use_figma で `figma.currentPage.findAll(n => n.reactions && n.reactions.length > 0).length` を全ページで集計
   - Reactions が 1 件も無い場合 → ワイヤーフレームレベルと判定し、README に「**プロトタイプ Reactions**: 未設定（ワイヤーフレームレベル）。アクションの遷移先はサブエージェントが構成要素から **客観推定** で記述します」と追記
   - Reactions が一部のみ設定されている場合 → 一部設定済と判定（混在モード）
6. 各ページのスラッグを決定
7. `docs/pages/README.md` の骨組みを作成（**Step 6 で横断サマリーを追記**）

### Step 2: 各ページ構造抽出（ページ単位で並列）

ページ数だけ Sonnet サブエージェントを **1 メッセージ内で並列起動**。

各サブエージェントの責務（[`references/sub-agent-prompts.md` の Step 2 テンプレート](references/sub-agent-prompts.md)）:
- `use_figma` でフレーム階層を取得
- `docs/pages/<slug>.md` を生成し、以下を含める：
  - ページ見出し（タイトル / ノードID / **ページの役割概要**）
  - **構成要素一覧表**（構成要素名 / 種類 / ノードID / 役割概要）
  - 詳細セクション

「ページの役割概要」は **ページ名称＋構成要素から客観的に導ける範囲で 1〜2 文で記述する**（推測補完しない範囲で）。例：「秋田書店まんが賞ポータルのトップページ。注目賞のヒーロー表示、ステータスフィルター付き賞カード一覧、ニュース、特集記事、Web 持ち込み CTA、フッターで構成される」。

### Step 3: 各ページのアクション抽出（ページ単位で並列）

Step 2 完了後、ページ単位で Sonnet サブエージェントを並列起動。

各サブエージェントの責務：
- `docs/pages/<slug>.md` を Read
- **アクションボタン一覧表** を追記（構成要素名 / ノードID / アクション種別 / 挙動概要）
- アクション種別は語彙制限あり（ページ遷移、外部リンク、ページ内アンカー、オーバーレイ表示、オーバーレイ閉じる、一覧フィルター、スライド切替、アコーディオン展開/折りたたみ、テキスト入力＋検索送信、履歴戻る）
- 挙動概要は **構成要素名・親要素・アイコンから客観的に導ける範囲で 1 文で記述**（推測補完しない範囲で）

### Step 4: ユースケース抽出（親エージェント / Opus）

1. `docs/pages/` 全件を Read
2. ページ間の動線・アクションから **明示的に読み取れる** ユースケースを列挙
3. `docs/use-cases.md` を生成
4. **チェックポイント**: ハイブリッドモードでは UC 一覧サマリをユーザーに提示し「不足／違和感の修正要否」を確認

各 UC の必須フィールド：
- **UC-XX**（ID）
- **ユースケース名**
- **ユースケースカテゴリ**（複数 UC をグルーピング。例: 「賞の発見」「応募」など）
- **目的**
- **シナリオ**（手順 1〜N）
- **前提のユースケース** / **後続のユースケース**（無ければ「なし」）
- **データ更新の有無**（「あり」/「なし」 + 簡潔な内容）

**Figma に動線が無い操作は UC として記載しない**。

### Step 5: アクター抽出 + UC×Actor マトリクス（親エージェント / Opus）

1. `docs/use-cases.md` を Read
2. 各 UC のシナリオに登場するアクターを集約
3. Figma 上のテキスト（コピー、対象読者を示唆する文言、想定読者向け CTA、SNS リンク、フッター、SEO 用途）から **読み取れる範囲のアクター**（プライマリ／セカンダリ／オフステージ）を最大限抽出する
4. `docs/actors.md` を生成（**UC×Actor マトリクスとマトリクス考察を末尾に追加**）

各アクターの必須フィールド：
- **A-XX**（ID）
- **アクター名**
- **分類**（プライマリ / セカンダリ / オフステージ）
- **役割**
- **アクターが達成したいゴール**
- **典型ペインポイント**（Figma の解決対象から逆算できる範囲で。例：FAQ で解決される疑問、Status Filter で解決される選別など）
- **訪問頻度・利用デバイス**（Figma で読み取れる場合のみ。レスポンシブ仕様の有無、SNS リンクの有無等から推察可）
- **主なオペレーション**
- **ユースケース一覧**
- **ペルソナ例**（Figma の Hero コピー、CTA 文言、対象賞のジャンルから読み取れる場合のみ）

**UC×Actor マトリクス**（必須）:
- 行: UC、列: 全アクター
- 関与は「●」で示す
- マトリクス直後に「読み取れる事実」（X 件の UC が A-01 専用、共通 UC は Y 件、応募導線は何アクター中心 等）を散文で追記

### Step 6: 整合性レビュー + 横断サマリー追記（親エージェント / Opus）

#### Step 6a: 整合性レビュー（レポート出力のみ）

1. Step 0 のプロジェクトゴールを Read
2. `docs/use-cases.md` `docs/actors.md` `docs/pages/` を統合的に Read
3. 以下の不足を **検出して列挙**（修正は適用しない）：
   - **ゴールから見て足りない UC**
   - **ゴールから見て足りない Actor**
   - **UC から見て足りない Page**
   - **UC から見て足りない Action Button**
4. `docs/reviews/coverage-review.md` に結果を書き出し

#### Step 6b: 横断サマリー追記（pages/README.md への追記）

整合性レビューの所見を踏まえつつ、以下のセクションを `docs/pages/README.md` に追記：

- **共通要素（横断的な実装方針）**: 各ページに繰り返し登場する共通レイアウト（Header / Footer / Menu Overlay）、共通 UI パターン（Section Header / Card / CTA Button 等）の整理
- **サイト全体のインタラクション分布**: アクション種別ごとに発生場所をまとめた表
- **エンティティ／データ設計上の示唆**: ページ表示から導ける Entity 設計の方針（共通エンティティのライフサイクル、テンプレート切替条件等）
- **未確認・要追加情報**: Figma 未提供のため別途仕様確認が必要なページ・フォーム・遷移先

この追記は「整合性レビューのサマリーを開発者向けに翻訳したもの」と位置づけ、レビュー結果と整合させる。

### Step 7: データモデル抽出（親エージェント / Opus）

1. `docs/pages/README.md` の **「エンティティ／データ設計上の示唆」** セクション（Step 6b で追記済み）を Read。これがデータモデル設計の起点となる
2. `docs/pages/` 全件を Read
3. 表示要素・アクションから **明示的に読み取れる** データ要素を Entity / Relation に分類
4. `docs/data-model.md` を生成（**状態遷移セクションと設計上のメモ必須**）
5. **チェックポイント**: ハイブリッドモードでは Entity 一覧サマリをユーザーに提示し「過不足の修正要否」を確認

#### 過剰定義の回避

「Figma に対応ページ／表示要素が存在しない汎用 Entity」（例: 一般的な `StaticPage`、`User`、`Session`、`AuditLog` 等）は **本体ドキュメントに定義せず**、`data-model-review.md` の「推奨アクション」で「以下の Entity が必要そう」と提案するに留める：

| 例 | 判定 |
|---|---|
| `Award`、`Article` 等、ページに表示要素がある | 定義する |
| `StaticPage`（運営会社・プライバシー等。本 Figma に未提供） | **定義しない**。レビュー側で提案 |
| `User`、`Session`（会員機能が Figma に無い） | **定義しない**。レビュー側で提案 |

各 Entity の必須フィールド：
- **E-XX**（モデルID）
- **モデル名**
- **概要**
- **PK**（カラムID で指定）
- **FK**（カラムID + 参照先 Entity）
- **属性一覧**（カラム表）
- **インデックス一覧**
- **状態遷移**（ENUM 型カラムを持つ Entity のみ。状態フロー図と各状態で必須/不要となるカラムを表で示す）

各カラム・インデックス・Relation の必須フィールドは従来通り。

**必須サブセクション**（ドキュメント末尾に追加）:
- **状態遷移と表示テンプレートの対応**: status 等の ENUM を持つ Entity について、状態遷移と表示テンプレート（pages/）の対応を表化
- **CMS / 運用上の留意**: 編集 UI のタブ分割提案、一括投入手段（CSV インポート等）、デフォルト値ルール
- **SEO / 構造化データに向けた追加検討**: OGP / JSON-LD 対応推奨フィールド、検索インデックスの方針
- **本データモデルに含めない要素**: 会員機能・認証・分析データ等の対象外要素を明示

これらは「Figma の構成から自然に導出されるベストプラクティス」であり、客観抽出の許容範囲。

### Step 8: 各ページにモデル参照を追記（ページ単位で並列）

Step 7 完了後、ページ単位で Sonnet サブエージェントを並列起動。

#### 親エージェントの責務（事前準備）

サブエージェント起動前に、`data-model.md` から **使用可能な Entity / カラム の ID リスト** を抽出し、各サブエージェントのプロンプトに含める：

```bash
# Entity ID と名前を抽出
grep -E "^### E-[0-9]+:" data-model.md
# 結果例: ### E-01: AwardSeries, ### E-02: Award, ...
```

抽出したリストをプロンプトの **「使用可能な Entity」** セクションに転記し、「**このリスト外の Entity / カラム番号を使用してはならない**」と明示する。

#### サブエージェントの責務

- `docs/pages/<slug>.md` と `docs/data-model.md` を Read
- 「参照モデル」セクションを追記
- **集約ルール（冗長性削減）**:
  - **同一カラムを参照する複数の表示要素は集約**（「賞名（ヘッダー）」「賞名（カード）」を別行で並べず、1 行に「賞名（複数箇所）」）
  - **静的文言は 1 行にまとめる**（フッターリンク 3 件を 1 行に集約）
  - **セクションあたりの行数の目安は 8 行以内**
- **対象ファイル以外への Edit 禁止**（他のファイルは Read のみ）
- **完了前のセルフチェック**: 追記後に対象ファイルを Read し、`## 参照モデル` セクションが正しく存在することを確認
- **完了報告に必須項目**: 追記したセクション名（正確に `## 参照モデル`）、利用 Entity 数、対応モデル未定義件数

#### 親エージェントの検証（事後）

全サブエージェント完了後、各ページに対して以下を確認：
```bash
grep "^## 参照モデル" docs/pages/*.md
```
全ページに 1 行ずつヒットすることを確認。欠けがあれば該当ページを再実行。

### Step 9: データモデルレビュー（親エージェント / Opus、出力のみ）

1. `docs/data-model.md` と `docs/pages/` 全件を Read
2. 以下を **検出して列挙**：
   - ページに表示要素があるのに対応する Entity / カラムが無い
   - Entity / カラム の過剰定義
   - FK の整合性
   - インデックスの過不足
3. `docs/reviews/data-model-review.md` に書き出してユーザーに提示

### Step 10: コンポーネント抽出（親エージェント / Opus）

1. `docs/pages/` 全件を Read
2. 表示要素を Atomic Design（Atoms / Molecules / Organisms / Templates / Pages）に分類
3. **冒頭に「共通化方針サマリー」セクションを配置**：
   - 統合した個別コンポーネント一覧（統合前 → 統合後 → 統合プロパティ）
   - 統合の判断基準（見た目／構造／コンテンツ／CMS フィールドの観点）
4. **ページ→Organism マッピング検証表を必須化**:
   - 各ページの構成要素一覧（Step 2 の H3 セクション群）と対応 Organism を表で並べる
   - **未対応の構成要素が無いことを確認**してから次のステップへ
   - 未対応があれば、その時点で新規 Organism を追加（Step 12 のレビューで指摘されるのを待たない）
5. `docs/components.md` を生成

#### ページ→Organism マッピング検証表（components.md 末尾に必須）

```markdown
## ページ→Organism マッピング検証

各ページの構成要素（H3 セクション）に対して、対応する Organism が定義されていることを確認する表。**未対応セルが 1 つでもあれば Step 10 を完了とせず Organism を追加する**。

### top.md
| 構成要素（ノードID） | 対応 Organism |
|---|---|
| Header (`98:64`) | `CMP-41` Header |
| Hero Section (`98:71`) | `CMP-43` HeroSlider |
| ... | ... |

### award-detail-result.md
| 構成要素（ノードID） | 対応 Organism |
|---|---|
| Header (`98:185`) | `CMP-41` Header |
| Result Hero (`98:195`) | `CMP-XX` ResultHero（新規追加） |
| Overall Comment (`98:201`) | `CMP-XX` OverallCommentSection（新規追加） |
| ...（全構成要素について 1 行ずつ） | ... |
```

各コンポーネントの必須フィールド：
- **CMP-XX**（コンポーネントID）
- **コンポーネント名**
- **概要**
- **Atomic Design における種別**
- **パラメータ一覧**
- **イベントハンドラ一覧**

**出力形式（冗長性削減）**:
- **Atom レベルは表形式に統合**（1 つの H2 セクション内で全 Atom を行として並べる、1 Atom = 1 H2 は廃止）
- **Molecule・Organism は H3 でコンパクトに**（パラメータ・ハンドラは小さな表で示す）
- 複雑なバリアントを持つコンポーネントのみ、追加説明を散文で記述

### Step 11: 各ページにコンポーネント参照を追記（ページ単位で並列）

Step 10 完了後、ページ単位で Sonnet サブエージェントを並列起動。

#### 親エージェントの責務（事前準備）

サブエージェント起動前に、`components.md` から **使用可能な CMP の ID リスト** を抽出してプロンプトに含める：

```bash
grep -E "^\| \`CMP-[0-9]+\`" components.md | grep -oE "CMP-[0-9]+" | sort -u
# または ### CMP-XX 形式から
grep -E "^### CMP-[0-9]+:" components.md
```

抽出したリストをプロンプトの **「使用可能な CMP」** セクションに転記し、「**このリスト外の CMP 番号を使用してはならない（CMP-70〜78 のような架空の番号を捏造しないこと）**」と明示する。

#### サブエージェントの責務

- `docs/pages/<slug>.md` と `docs/components.md` を Read
- 「利用コンポーネント」セクションを追記
- **集約ルール**:
  - 出力対象は **Organism / Template / 主要 Molecule のみ**（Atom レベルの Icon / Text / Divider 等は内包される設計のため省略）
  - 同一コンポーネントの複数利用箇所は「利用箇所数」に集計
  - ノードID の箇条書きはしない
- **対象ファイル以外への Edit 禁止**（他のファイルは Read のみ）
- **完了前のセルフチェック**: 追記後に対象ファイルを Read し、`## 利用コンポーネント` セクションが正しく存在することを確認
- **完了報告に必須項目**: 追記したセクション名（正確に `## 利用コンポーネント`）、ユニーク CMP 数、使用 CMP のリスト（親エージェントが使用可能 ID リストと突合可能にするため）

#### 親エージェントの検証（事後）

```bash
grep "^## 利用コンポーネント" docs/pages/*.md
```
全ページに 1 行ずつヒットすることを確認。さらに各ページで使われている CMP-XX が `components.md` に実在するかを検証：
```bash
# 各ページから CMP-XX を抽出し、components.md に存在するか確認
```
不一致があれば該当ページを再実行。

### Step 12: コンポーネントレビュー（親エージェント / Opus、出力のみ）

1. `docs/components.md` と `docs/pages/` を Read
2. 以下を **検出して列挙**（**各項目に優先度ラベル「必須／推奨／オプション」を付与**）：
   - ページに表示要素があるのに対応するコンポーネントが無い → 通常「必須」
   - コンポーネントが定義されているがどのページでも利用されていない → 通常「オプション」
   - 類似コンポーネントの共通化候補 → 通常「推奨」
   - パラメータ・イベントハンドラの過不足 → 内容により「必須／推奨／オプション」
3. `docs/reviews/components-review.md` に書き出してユーザーに提示

### Step 13: 各ページ末尾に「関連する未解決事項」を追記（ページ単位で並列）

Step 12 完了後、ページ単位で Sonnet サブエージェントを並列起動。

各サブエージェントの責務：
- 3 つのレビューレポート（coverage-review.md / data-model-review.md / components-review.md）を Read
- 自分が担当するページ（slug）に関連する不足項目を逆引きで抽出
- `docs/pages/<slug>.md` の末尾に「## 関連する未解決事項」セクションを追記
- **対象ファイル以外への Edit 禁止**（レビュー 3 ファイルは Read のみ）
- **完了前のセルフチェック**: 追記後に対象ファイルを Read し、`## 関連する未解決事項` セクションが正しく存在することを確認

#### 親エージェントの検証（事後）

```bash
grep "^## 関連する未解決事項" docs/pages/*.md
```
全ページに 1 行ずつヒットすることを確認。

#### 抽出ルール
- coverage-review の「足りない Page」「足りない Action」セクションで自ページが言及されているか
- data-model-review の「ページにあるがモデルに無い表示要素」で自ページの slug が記載されているか
- components-review の「ページにあるがコンポーネント未定義」で自ページの slug が記載されているか
- 該当する項目を **項目番号と概要 1 行**で列挙する（詳細は元レビュー文書を参照する形）

#### 出力フォーマット例

```markdown
## 関連する未解決事項

各レビューレポートで本ページに紐づく不足項目を逆引きしたサマリ。

- **整合性レビュー** ([reviews/coverage-review.md](../reviews/coverage-review.md)):
  - #1: 漫画賞一覧ページの実体が未定義（必須）
  - #4: 「選考中」状態のカード遷移先ページ実体が未定義（推奨）
- **データモデルレビュー** ([reviews/data-model-review.md](../reviews/data-model-review.md)):
  - なし
- **コンポーネントレビュー** ([reviews/components-review.md](../reviews/components-review.md)):
  - #1: Result Hero Organism の追加（必須）

該当無しの場合は「該当なし」と記載。
```

## 並列起動の実装パターン

ステップ単位の並列起動は、**1 メッセージ内で複数の Agent ツール呼び出しを並べる** ことで実現する：

```js
// Step 2 並列起動の擬似コード
const pages = ["top", "award-detail-open", "award-detail-result", ...];
const agents = pages.map(p => Agent({
  description: `${p} 構造抽出`,
  subagent_type: "general-purpose",
  model: "sonnet",
  prompt: extractStep2Prompt(p),
}));
```

Step 2 / 3 / 8 / 11 が **ページ単位で並列化** されるステップ。

## ハイブリッド対話のチェックポイント

| タイミング | 確認内容 | スキップ条件 |
|---|---|---|
| Step 0 | Figma URL / プロジェクトゴール / 転記先 / 出力先 | すべて提示済み |
| Step 1 後 | 抽出ページ一覧と除外判定 + キャンバスサイズ検出結果 | 全自動モード時 |
| Step 4 後 | UC 一覧サマリ（任意） | 全自動モード時 |
| Step 7 後 | データモデル Entity 一覧サマリ（任意） | 全自動モード時 |
| Step 6 後 | 整合性レビュー結果（優先度ラベル付） | スキップ不可 |
| Step 9 後 | データモデルレビュー結果（優先度ラベル付） | スキップ不可 |
| Step 12 後 | コンポーネントレビュー結果（優先度ラベル付） | スキップ不可 |
| Step 13 後 | 各ページの「関連する未解決事項」が追記されたことの確認 | 全自動モード時 |

レビューステップは **必ずユーザーに結果を提示** する。スキルは修正を適用しない。

## エラー時の挙動

- Figma MCP 未認証 → `/mcp` での認証を促す
- ノードID エラー → URL の fileKey 部分を確認、ユーザーに再提示を依頼
- サブエージェント失敗 → 親が直接リトライ（Sonnet → Opus フォールバック）
- 出力ファイルが既存 → 上書き／追記／中止をユーザーに確認
- 「Figma 未記載」項目が多い → そのまま「未記載」表記で進める（レビューステップで列挙される）

## 仕上げ

全 13 ステップ完了後、**最終検証を必須化**：

### 最終検証チェックリスト（親エージェントが必ず実行）

```bash
# 1. 全ページに 6 セクションが揃っているか
for f in docs/pages/*.md; do
  if [ "$(basename $f)" != "README.md" ]; then
    echo "=== $f ==="
    grep "^## " "$f"
  fi
done
```

期待される 6 セクション（順序固定）:
1. `## 構成要素`
2. `## テキスト要素一覧`
3. `## アクションボタン`
4. `## 参照モデル`
5. `## 利用コンポーネント`
6. `## 関連する未解決事項`

欠けがあれば該当ステップを再実行する。

### Entity / CMP の整合性検証

```bash
# 各ページで使われている E-XX / CMP-XX が data-model.md / components.md に実在するか
grep -ho "E-[0-9]\+" docs/pages/*.md | sort -u > /tmp/used_entities.txt
grep -ho "E-[0-9]\+" docs/data-model.md | sort -u > /tmp/defined_entities.txt
diff /tmp/used_entities.txt /tmp/defined_entities.txt
# CMP も同様
```

ページで使われている ID がマスタに無ければ、サブエージェントが番号を捏造した可能性が高い。該当ページを再実行。

### 完了報告

1. 生成ファイル一覧と各ファイルの行数を提示
2. 3 つのレビューレポートのサマリ（不足検出数 + 優先度別件数）を提示
3. ユーザーが手動で対応すべき **必須項目** を抽出して提示
4. **最終検証結果**（セクション完備、ID 整合性 OK の確認）も明示
